# Security model

Проект обрабатывает реальные деньги и доступ к operational hot wallet. Production запускается
только после выполнения [`PRODUCTION_CHECKLIST.md`](PRODUCTION_CHECKLIST.md), успешного preflight
и тестовой оплаты ЮKassa без реальной покупки Stars.

## Финансовые инварианты

- Клиент не передаёт итоговую сумму: количество, цена и сумма вычисляются сервером и сохраняются
  в заказе до создания платежа.
- Заказ допускается к покупке Stars только после server-to-server проверки платежа ЮKassa через
  `GET /v3/payments/{payment_id}` и точного совпадения суммы, валюты и metadata.
- Redirect `return_url` не подтверждает оплату. Webhook также не считается доказательством сам по
  себе: он только запускает повторную проверку через API провайдера.
- Повторный webhook и ручная сверка идемпотентны. Уникальные provider ID и guarded transitions не
  позволяют оплатить или исполнить один заказ дважды.
- Для каждого POST в ЮKassa используется стабильный `Idempotence-Key`; возврат имеет отдельный
  ключ.
- Неопределённый результат POST в Fragment без сохранённого request ID никогда не повторяется
  автоматически. Такой заказ переводится в ручную проверку.
- Возврат ЮKassa запрещён, пока покупка Fragment выполняется, завершена либо имеет неопределённый
  результат.
- Test-магазин ЮKassa не может быть одновременно включён с реальной покупкой Stars.

## Публичная поверхность

Через Caddy публичны только:

- `POST /webhooks/yookassa`;
- `GET /payments/return`;
- стандартные порты `80/443`, необходимые для HTTPS и перенаправления.

Webhook принимает только JSON нужного размера и известной схемы, ограничивается по частоте и
возвращает `200` только после безопасной обработки. В коде нет выдуманной проверки подписи:
подлинность результата подтверждается запросом к API ЮKassa. Админка слушает только
`127.0.0.1:8080` и открывается оператором через SSH-туннель.

## Секреты и кошелёк

- Секреты не записываются в image, репозиторий, URL, frontend, localStorage или логи.
- Production использует Docker secrets: Bot token, Telegram API hash/session, ЮKassa secret,
  database passwords и seed хранятся отдельными файлами с минимальными правами.
- Seed доступна только `purchase-worker` через read-only mount. Bot, gateway, admin, Caddy и БД её
  не получают.
- Fragment KYC cookies также доступны только `purchase-worker`; preflight получает их временно
  для локальной проверки формата. Инструкция ротации: `docs/FRAGMENT_KYC_SETUP.md`.
- Для сервиса нужен отдельный hot wallet с небольшим дневным остатком; основной кошелёк здесь не
  используется.
- Логи очищают authorization, token, password, seed, cookie и ключ ЮKassa.

Если секрет попал в терминал, чат, архив или историю VCS, удаления строки недостаточно: credential
нужно отозвать и выпустить заново. Telegram session и seed считаются секретами того же уровня.

## Админка и база данных

- Доступ разрешён только numeric Telegram ID из allowlist; пароль хешируется, поддерживается TOTP.
- Изменяющие запросы защищены CSRF, опасные действия требуют явной фразы подтверждения и пишутся
  в audit log.
- PostgreSQL не публикует порт. Financial transitions выполняются в транзакциях с row locks,
  уникальными ограничениями и durable outbox.
- PostgreSQL advisory lock разрешает только один активный Telegram polling process.
- SQLite предназначен только для локальной разработки; production-конфигурация его отвергает.

## Эксплуатация и инциденты

- Первый запуск: `MAINTENANCE_MODE=true`, `PURCHASES_ENABLED=false`.
- Настраиваются ежедневные backup, off-host копия, проверка восстановления, log rotation и alerts
  по ошибкам провайдеров, ручной проверке и низкому остатку hot wallet.
- При подозрении на компрометацию: выключить покупки, остановить worker, вывести остаток с hot
  wallet, отозвать credentials/session, сохранить логи и audit trail, затем восстановить сервис с
  новыми секретами.
- Реальный возврат или покупка не выполняются для диагностики без отдельного подтверждения
  владельца.

## Обязанности владельца до live

Владелец должен получить и проверить ЮKassa credentials, принять решение по чекам/54-ФЗ с
ЮKassa или бухгалтером, настроить DNS/HTTPS/firewall, заполнить production secrets, проверить
restore backup и вручную одобрить одну минимальную контролируемую live-покупку.
